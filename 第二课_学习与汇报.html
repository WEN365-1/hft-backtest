先建立框架

一句话：把历史行情“重新开一家交易所”

第二课的核心不是预测涨跌，也不是马上赚钱，而是建立一个可信、可复用、可验证的行情环境。策略以后只需要面对统一接口，不用关心数据来自历史文件还是实时网络。

第一课像“把过去的市场录像看了一遍”；第二课是“做了一个播放器，还能同时放给多个策略看”。录像卡顿时明确告诉大家暂停，恢复后再继续，绝不偷偷跳过去。
采集→存储→回放→订单簿→策略

本课最重要的是数据可信度；策略收益不是本课目标。

为什么按本地接收时间回放？

本地接收时间（recv_ts_ms）是策略真正有机会看到事件的时间。交易所事件时间（E/T）描述交易所何时产生事件。用 E/T 决定策略何时能看到数据，会忽略网络传输，让回测里的策略比实盘“更早知道”。

比赛录像在 10:00:00 拍摄，但你 10:00:01 才收到。回测时不能在 10:00:00 就假装自己看过。

模块 1—3

采集 → 存储 → 回放

1. 采集：不仅保存“内容”，也保存“何时收到”

现货订阅 depth@100ms 与 aggTrade；U 本位订阅 depth@100ms 与逐笔 trade。两者都保留成交方向、价格和数量，区别是 aggTrade 会聚合同一吃单的部分成交，trade 更细。深度事件保存 E/U/u/pu/b/a，成交保存 E/T/p/q/m，所有事件都加 recv_ts_ms。每 60 秒通过 REST 获取快照，重连后再立即获取。

快照像一张完整合照，增量像之后的每一处改动。只有改动没有合照，很难知道最初每个人站在哪里。

2. gap：异常本身也是数据

gap表示行情连续性中断。断线时写入一条带原因和接收时间的 gap，而不是只留一句控制台日志。重连采用指数退避（exponential backoff）：1、2、4……最多 30 秒，避免故障时疯狂重连。

不是把“缺席”伪装成“一切正常”。缺页要先标记，恢复后从新的合照重新开始。

3. Parquet 分区与追加写

Parquet是列式存储格式，适合大量结构化行情；ZSTD负责压缩。目录为：

root/spot/BTCUSDT/date=2026-10-26/hour=08/batch=时间戳-UUID.parquet
root/usdm/BTCUSDT/date=2026-10-26/hour=08/batch=时间戳-UUID.parquet

每分钟写一次，文件名含 UUID，因此不会覆盖。实时事件的 UTC 日期和小时按接收时间计算；明确标记的历史补录按成交发生时间进入研究分区，实际下载时间仍原样保留。

4. 流式回放与 k 路归并

流式回放指读一批、处理一批；k 路归并是把多个各自有序的文件流，用最小堆不断取出当前最早事件。排序键 replay_time_ms 对实时事件等于 recv_ts_ms，只对历史补录等于成交时间 T。

打开文件 → 每个文件读一个 batch → 各取队首
       → 最小堆选 replay_time_ms 最早者 → 推给交易所
       → 从同一文件补下一条 → 重复直到结束
几张已经按时间排好的长桌，每次只比较各桌最前面的卡片，拿最早的一张。不必把所有卡片搬到一个房间。历史补页会插回发生时的位置，但补页上仍盖着“后来下载”的章，不能假装当时在线收到。

工程边界：内存主要随“文件数 × batch 大小”增长，不随总时长线性增长；大量小文件仍需在生产中合并优化。

最容易追问

订单簿：现货和 U 本位不能套同一规则

L2 订单簿按价格聚合数量。本地维护两个字典：买价→买量、卖价→卖量。数量为 0 表示该价位删除；排序后买价从高到低、卖价从低到高。

阶段现货 SpotU 本位 USD-M
新快照设置簿和 lastUpdateId相同
第一条衔接事件快照应覆盖到首个增量衔接点相同
后续连续性U ≤ last + 1 ≤ upu == last
旧事件忽略，不重复修改忽略，不重复修改
缺页标为未同步，暂停推送相同
现货看“这一页有没有包含下一页页码”；U 本位看“这一页背面写的上一页页码，是否正好等于我手里的页码”。

为什么不能缺页后继续？

漏掉一次数量更新后，后续价格排序和深度都可能错误。继续推送等于让策略拿着假盘口做决策。本实现顺序是：

发现 gap→on_status→暂停该标的→新快照→ready→继续

前 20 档一致率怎么计算

新快照到达时，只有本地簿与快照的 lastUpdateId 相同才比较；快照领先就暂存并等本地增量追上，本地已超过或单个聚合事件跨过编号则分别记为跳过。健康簿继续做增量，不用较旧快照倒退重置，只有未同步时才用快照重建。若重置后再比较，必然 100%，没有验证意义。

一致率 = 前 20 档完全一致的次数 / 有效快照比较次数

真实市场中快照与增量存在毫秒级错位，可能产生少量差异；低于 95% 要排查丢包、衔接和时间对齐。

同一时间顺序

数据隔离

每个回调拿到深拷贝，一个策略修改字典不会污染其他策略。

异常隔离

某个策略抛异常会被记录，其他策略和主回放继续。

数据源可替换

实时源实现相同 events()，策略代码不变。

像同一场直播：每个观众看同样内容；一个观众那边出故障，不让整场直播停掉；以后换直播源，观众不用换操作方式。

示例策略在算什么

  • 中间价 mid =（买一价 + 卖一价）/2；
  • 价差 spread = 卖一价 − 买一价；
  • 主动买卖量差 = 主动买量 − 主动卖量；m=true表示买方是 maker，所以是主动卖，数量记负。

每秒最多形成一条样本，滚动窗口只保留过去 1 秒成交，并按市场分别维护，避免现货成交混入 U 本位指标。

为下一课铺路

市价单、限价单与排队

市价单：按对手方深度逐档成交

市价单（market order）优先立即成交。买单从卖一开始向上吃，卖单从买一向下吃；可能跨档和部分成交，产生滑点。不能假设任意大数量都在最优价全部成交。

买 3 杯奶茶，第一家只剩 1 杯，就得再去下一家买 2 杯；平均价格不是第一家的标价。

限价单：价格到了，不代表轮到你了

限价单（limit order）若穿过对手价，可先按吃单处理；否则进入同价位队列。被动成交遵循价格优先、时间优先。价格被穿过通常可成交；仅被触及时，要结合前方队列和成交量。

L2 队列估计

挂单到达：queue_ahead = 该价位当时可见总量
同价成交：先扣 queue_ahead，归零后才轮到我的订单
同价新增：排在我后面，不影响 queue_ahead
同价减量：按撤单模型分配，且避免与成交重复扣减
撤单模型含义结果倾向
RiskAverse减量全在我后面最保守，只有成交让队列前进
概率模型按相对位置分配前后撤单中间基准
队首撤单减量全在我前面乐观边界，容易高估成交
你只看见队伍总人数变少，不知道走的是你前面还是后面的人。所以只能做几种假设，报一个范围，不能声称精确。

我们下一课的撮合顺序

策略发单 → 风控 → 下单进入延迟 → 到达撮合引擎
→ 若可立即成交：走档 / 限量 / 部分成交
→ 否则：进入 FIFO 队列并估计前方数量
→ 成交与撤单事件推进队列
→ 计 maker/taker 费 → 原子更新订单与账户 → 响应延迟后通知策略

官方参考：hftbacktest Order Fill。回放市场不会因我们的订单改变，因此“大单无市场冲击”是必须披露的假设。

三种不同延迟

看到市场、订单到达、收到回报不是同一时刻

术语专业定义大白话与影响
Feed latency
行情延迟		交易所发送到本地接收你看到的是旧盘口；用 E/T 直接回测会太乐观
Order entry latency
下单进入延迟		本地发单到撮合引擎处理更晚成交、排更后；撤单也可能来不及
Order response latency
订单响应延迟		引擎处理到本地收到回报更晚知道真实持仓，可能重复下单或延迟风控
交易所事件 E/T → 行情延迟 → recv_ts_ms（策略看见）
策略发单 req_ts → 进入延迟 → exch_ts（交易所处理）
交易所处理 → 响应延迟 → resp_ts（策略知道结果）
不要说“加延迟后每笔一定更差”。单次噪声可能让某笔更好；应通过多时段、分布和压力情景检验系统性影响。

“这次我把第一课的单次回测脚本升级成了一个可复用的模拟交易所行情层，分成采集、存储、回放和订阅推送四块。

采集同时支持现货和 U 本位，保存交易所事件时间、成交时间和本地接收时间；每分钟拍快照，断线写 gap，重连后重新快照。存储用 Parquet，按市场、交易对、日期、小时分区，每分钟追加新文件。回放不是一次全读，而是分批读取并做多路归并。实时数据严格按本地接收时间推给策略，避免前视；后来补取的历史数据只按明确标记的 replay 时间参与研究回放。

订单簿部分我区分了现货和 U 本位的同步规则：现货检查 U/u 是否覆盖下一编号，U 本位检查 pu 是否等于上一最终编号。发现缺页会先通知策略并暂停，等快照恢复后继续。多个策略收到相同数据，单个策略报错不会拖垮其他策略。

主动准备追问

导师可能怎么问

为什么不用交易所时间 E/T 排序？

对实时数据，E/T 描述事件在交易所发生的时间，recv_ts_ms 描述本地何时能看见，策略决策必须以后者为信息边界；E/T 仍保留，用于估计行情延迟和诊断。唯一例外是明确标记的历史补录：它本来就不是当时在线收到的，研究回放用 replay_ts_ms=T 放回历史位置，同时保留真实下载时间。

为什么 Parquet 每分钟写一个文件，而不是每条追加？

Parquet 适合批量列式写入，每条写会产生大量小文件和开销。每分钟是实时性与写放大的折中；代价是崩溃时可能损失尚未写盘的一分钟缓冲。

为什么现货用 U/u，U 本位还看 pu？

两个市场的增量同步协议不同。现货可用事件区间覆盖下一编号判断连续；U 本位用 pu 串联上一事件最终编号。混用会把正常事件误判缺页，或漏掉真正缺页。

为什么一致率不是重置快照后计算？

重置后本地簿就是快照，比较恒等，无法证明增量回放正确。但直接在新快照到达时比较也不严谨：两边 lastUpdateId 不同，代表不同市场状态。正确做法是等本地增量追到快照同一编号再比较；旧快照或被聚合事件跨过编号的快照单列，不塞进成功分母。

一个策略报错为什么不让整个系统停止？

模拟交易所需要保证多个独立研究策略互不干扰。异常会记录并隔离；如果将来是实盘关键风控策略，则应另设 fail-fast 或降级机制，不能机械沿用研究环境的容错策略。

L2 能不能精确算排队位置？

不能。只能看到价位聚合量，看不到逐单 ID。新单前方量可初始化，但后续撤单发生在哪里不可知，因此需要保守、概率、乐观模型和实盘校准。

价格碰到限价单，为什么不一定成交？

同价前已有订单，成交量可能只够消化前方队列。只有价格穿过或轮到队首并有足够对手成交量，才成交。

多个策略收到“完全一样”怎么保证？

同一排序事件流、同一主题发布、每份深拷贝，并用完整样本序列比较验证，而不是只比较最终值。

真实 24 小时做完了吗？

还没有。旧批次明确未通过；新批次已于 2026-10-28 01:10:51 开始独立连续录制，目前正在进行。约 1.51 小时中途质量检查通过，但必须等六个频道都覆盖满 24 小时并通过最终验收，才能回答“已完成”。

为什么 U 本位改用 trade，而不是 aggTrade？

实测 aggTrade 的单流、合并流和主动订阅都持续无消息，同一主机 trade 能稳定收到真实成交。trade 粒度更细，并保留本课需要的 E/T/p/q/m，因此可用于统一成交推送；历史缺口用 REST aggTrades 补齐，但实时逐笔与历史聚合的粒度差异必须披露。

补录会不会伪造接收时间或重复首条实时成交？

不会。补录 recv_ts_ms 是 REST 实际下载时间，交易所 E 留空，T 同时写入 trade_ts_ms 和 replay_ts_ms。脚本先找到第一条实时成交的 T，只补该时间之前的数据，并按聚合成交 ID 翻页，避免同毫秒漏单；完整清单存在时重复执行不会再次写数。

下一课最难的是什么？

不是生成一个 fill，而是保证时序：订单尚未到交易所不能成交，撤单在途仍可能成交；还要处理排队、部分成交、费用与账户原子更新。
